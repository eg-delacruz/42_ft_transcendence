1. CONTEXT / CURRENT STATE (from 2026-10-12 audit)
================================================================
- No public API secured by an API key exists.
- All REST routes (/api/auth, /api/users, /api/games) require an
  HttpOnly `access_token` JWT cookie via `authMiddleware`
  (backend/src/middlewares/auth.middleware.ts) + `requireRole`
  (backend/src/middlewares/role.middleware.ts).
- The only `apiKey` string in the repo is Swagger's `cookieAuth`
  scheme (backend/src/config/swagger.ts:68):
    cookieAuth: { type: 'apiKey', in: 'cookie', name: 'access_token' }
  This is NOT a real API key.
- No API-key issuance, storage, validation, `x-api-key` header
  check, or API_KEY env var exists.
- `VITE_CLIENT_HEADER_KEY` in backend/src/config/env.ts is dead
  config: declared with default "defaultclientkey" but never read
  anywhere; absent from .env / .env.example.
- Exposed surfaces today: /api (JWT cookie), /api-docs (dev-only,
  NODE_ENV != production), /uploads static.
- SECURITY HOLE: DELETE /api/clear-db (backend/src/routes/index.ts:20)
  is unauthenticated and wipes User + Game collections. Marked
  "TODO: erase when project is ready". Must be removed/protected
  as part of this work.

Goal: add a separate public, key-secured API namespace for
database interaction, without weakening the existing cookie-JWT
app API.

2. DECISIONS NEEDED (resolve before coding)
================================================================
[ ] Single global key vs. per-client keys?
    Recommended: per-client keys (issuable, revocable, scoped).
[ ] Header name: `x-api-key` (recommended standard).
[ ] Key format: random prefix (for lookup, e.g. `ft_pk_...`) +
    secret part (only shown once at creation).
[ ] Storage: hash secrets (SHA-256 at minimum; bcrypt/scrypt if
    login-rate), never store plaintext. Store prefix + hash +
    name, scopes, expiresAt, revokedAt, createdBy, lastUsedAt.
[ ] Scopes: at minimum `read` vs `write`; decide which collections
    / endpoints are public (e.g. games leaderboard read, limited
    user public fields) vs. internal-only.
[ ] Rate limiting + audit logging for key usage: yes/no, limits.

[ ] 3.1 Data model
    - New Mongoose model `ApiKey` (e.g.

      prefix (unique, indexed), keyHash, name, scopes[],
      expiresAt?, revokedAt?, createdBy (admin user ref),
      lastUsedAt, createdAt/updatedAt.
    - Add `apiKey` reference/fields nowhere else; User model
      needs NO apiKey field (keys live in their own collection).

[ ] 3.2 Key issuance + management (admin-only, cookie-JWT + role)
    - POST /api/api-keys (super_admin, admin): create key, return
      plaintext secret ONCE + prefix + metadata.
    - GET /api/api-keys: list metadata (never secrets/hashes).
    - POST /api/api-keys/:id/revoke: set revokedAt.
    - DELETE /api/api-keys/:id: delete record.
    - All management routes use existing authMiddleware +
      requireRole, NOT the new apiKeyMiddleware.

[ ] 3.3 API-key auth middleware
    - New backend/src/middlewares/apikey.middleware.ts:
      * Read header `x-api-key` (exact match, no fallback to
        query params).
      * Parse prefix -> lookup DB -> timing-safe compare of
        hash(secret) with stored keyHash.
      * Reject missing (401), invalid (401), expired/revoked (401/403).
      * Attach req.apiKey { id, name, scopes } (distinct from req.user).
      * Update lastUsedAt (fire-and-forget, no request blocking).
    - No JWT cookie accepted on public namespace; no API key
      accepted on internal /users, /games, /auth/me routes.

[ ] 3.4 Public namespace (separate from app API)

    - Start minimal + read-only, e.g.:
      * GET /api/public/games/:game_name (public leaderboard view)
      * GET /api/public/users/:id/public (whitelisted fields only:
        display_name, avatar_url, points, stats, NOT email/password)
    - Add scope check middleware (requireApiScope('read'/'write')).
    - POST/PATCH only if the subject module requires writes; keep

4. ACCEPTANCE CRITERIA
================================================================
- External client with ONLY an API key (no cookie/JWT) can call
  /api/public/* successfully via `x-api-key` header.
- Missing/invalid/revoked/expired key is rejected; no data leaks
  (no emails, password hashes, or full user docs in public payloads).
- Keys are stored hashed; plaintext secret exists only in the
  single creation response.
- Admins can create, list, revoke keys via cookie-authenticated
  management endpoints.
- Swagger documents both schemes distinctly (cookieAuth vs apiKeyAuth).
- DELETE /api/clear-db hole is closed.
- Dead `VITE_CLIENT_HEADER_KEY` is resolved (removed or documented).

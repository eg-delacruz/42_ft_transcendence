Pasos para implementar WebSockets escalables (Socket.IO + Redis Adapter)

Objetivo
- Añadir comunicación en tiempo real robusta y escalable usando Socket.IO en el backend y `socket.io-client` en el frontend, sincronizando múltiples réplicas con Redis (pub/sub).

Prerrequisitos
- Usar `pnpm` (repositorio ya usa pnpm).
- Variables de entorno a definir: `REDIS_URL`, `JWT_SECRET`, `BACKEND_URL` (o `WEBSOCKET_URL`).

Instalaciones básicas
- Preferible (desde el host):
  - Backend: `pnpm --dir backend add socket.io ioredis @socket.io/redis-adapter`
  - Frontend: `pnpm --dir frontend add socket.io-client`

- Si necesitas instalar dentro de contenedores (opción requerida en algunos entornos):
  1) Levanta los contenedores en modo desarrollo para tener acceso a los servicios:
     - `make up`  (o `docker compose up -d --build`)
  2) Instalar dentro del contenedor del backend (uno-liner):
     - `docker compose exec backend pnpm add socket.io ioredis @socket.io/redis-adapter`
     - Si el contenedor no incluye `pnpm` en PATH, abre un shell e instala ahí:
       - `docker compose exec backend sh`  # o `bash` según la imagen
       - Dentro del contenedor: `pnpm add socket.io ioredis @socket.io/redis-adapter`
  3) Instalar dentro del contenedor del frontend (uno-liner):
     - `docker compose exec frontend pnpm add socket.io-client`
  4) Notas sobre persistencia de dependencias:
     - Si los `node_modules` están contenidos dentro de la imagen (no montados), instala con `docker compose exec` modificará la imagen en ejecución pero no la imagen base; considera reconstruir la imagen para producción.
     - Si el servicio monta la carpeta del proyecto desde el host (volumen), las dependencias instaladas en el contenedor quedarán reflejadas en el host.

Nota: instalar desde el host con `pnpm --dir` es más directo para desarrollo local. Usar la vía del contenedor cuando el flujo de trabajo o la CI lo requiera.

Resumen de archivos a editar (ubicaciones propuestas)
- `backend/src/index.ts` o `backend/src/app.ts` — inicializar Socket.IO y Redis Adapter.
- `backend/src/config/env.ts` — añadir `REDIS_URL` y lecturas de variables.
- `backend/src/modules/auth/*` — (usar o exponer función de verificación JWT para handshake).
- `backend/src/modules/*` — crear handlers/namespaces (`/chat`, `/match`, etc.).
- `frontend/src/hooks/useAuth.tsx` o `frontend/src/hooks/useSocket.tsx` — conectar cliente con token y reconexión.
- `docker-compose.yml` — añadir servicio `redis` y (opcional) modificar backend para múltiples réplicas en despliegue.

Pasos detallados (orden recomendado)
1) Añadir dependencias
  - Ejecutar los comandos de instalación indicados en "Instalaciones básicas".

2) Añadir Redis a `docker-compose.yml`
  - Añadir un servicio `redis` con persistencia mínima para desarrollo:
    redis:
      image: redis:7-alpine
      ports:
        - "6379:6379"
      volumes:
        - redis-data:/data
  - Añadir `volumes:` al final si no existe.

3) Configuración de entorno
  - Añadir `REDIS_URL=redis://redis:6379` en `.env` (desarrollo docker).
  - Asegurarse de que `JWT_SECRET` y demás ya estén configuradas.

4) Inicializar Socket.IO en el backend
  - En `backend/src/index.ts` (donde se crea el servidor `http`), envolver la app Express con `http.createServer(app)` y crear `new Server(httpServer, { cors })`.
  - Ejemplo de pasos:
    - Crear `httpServer` a partir de `app`.
    - Inicializar `io = new Server(httpServer, { cors: { origin: process.env.FRONTEND_URL || '*' } })`.

5) Conectar Redis Adapter
  - Usar `ioredis` o `redis` (según preferencia). Crear `pubClient` y `subClient = pubClient.duplicate()`.
  - Conectar ambos clientes y aplicar `io.adapter(createAdapter(pubClient, subClient))`.

6) Añadir middleware de autenticación para handshake
  - Implementar `io.use(async (socket, next) => { /* verificar token JWT */ })`.
  - Leer token desde `socket.handshake.auth.token` o `socket.handshake.headers.authorization`.
  - Verificar token con la función existente en `modules/auth` o con `jsonwebtoken.verify` y adjuntar `socket.user`.

7) Definir namespaces y handlers
  - Crear namespaces por dominio: `io.of('/chat')`, `io.of('/match')`.
  - Dentro de cada namespace: `on('connection', socket => { socket.join(roomId); socket.on('event', handler) })`.
  - Emplear rooms para chats/partidas y emitir a `namespace.to(room).emit()`.

8) Gestión de estado y presencia en Redis
  - Guardar mapping `userId -> socketId(s)` en Redis (sets o hashes) para permitir mensajes directos desde cualquier réplica.
  - Al desconectar, eliminar del set y opcionalmente marcar última conexión con TTL.

9) Limpieza y límites
  - Implementar rate-limits por socket (ej: 10 eventos/seg) y límites de tamaño.
  - Sanitizar payloads antes de procesar o guardar.

10) Frontend: conexión y rejoin
  - Crear un hook `useSocket` que:
    - Lea `accessToken` del estado (`useAuth`), cree `io(backendUrl, { auth: { token } })`.
    - Maneje `connect`, `disconnect`, `reconnect_attempt` y re-join de rooms tras reconexión.
    - Implemente backoff exponencial y reautenticación si token expiró (usar refresh token flow existente).

11) Docker / despliegue
  - En producción, ejecutar varias réplicas del backend y usar Redis adapter.
  - Usar un reverse proxy que soporte WebSockets (NGINX, Traefik) y TLS.
  - No depender de sticky sessions cuando el adapter esté activo.

12) Observabilidad y pruebas
  - Añadir métricas (Prometheus) y logs estructurados por evento.
  - Crear pruebas de carga con `autocannon` o `k6` simulando múltiples sockets y rooms.

13) Migración incremental y despliegue
  - Implementar en una rama feature, desplegar en staging con `redis` y 2 réplicas de backend.
  - Verificar intercambio de eventos entre réplicas (emit de réplica A recibido por sockets conectados a réplica B).
  - Hacer pruebas de fallo: matar una réplica y verificar reconexión y persistencia de presencia.

Checklist de validación
- Socket.IO inicializa y acepta conexiones autenticadas.
- Eventos entre réplicas se sincronizan (Redis pub/sub funciona).
- Frontend se reconecta y reingresa a rooms.
- No hay fugas de memoria ni datos residuales en Redis tras disconnect.
- Latencia y RPS aceptables según pruebas de carga.

Notas de seguridad y buenas prácticas
- No enviar JWT en query string sin TLS.
- Limitar tamaño de mensajes y sanitizar.
- Validar permisos de usuario antes de unirse a rooms.
